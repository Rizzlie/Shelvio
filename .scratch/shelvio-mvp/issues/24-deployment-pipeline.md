# Deployment pipeline and environments

Type: grilling
Status: resolved
Blocked by: 23
Map: [Shelvio MVP](../map.md)

## Question

How does Shelvio get from a commit to production, and which environments exist?

Known so far:
- [Hosting and file storage](04-hosting-and-storage.md): Render (Nest, Frankfurt), Cloudflare Pages (Angular), Neon (Postgres, Frankfurt), Cloudflare R2 (images).
- [Authentication and sessions](08-authentication.md) and [Covers, photos and thumbnails](11-covers-photos-thumbnails.md): custom domain bought by the user, DNS on Cloudflare Free, `app.`/`api.`/`img.` subdomains.
- [Technical foundations](15-foundations.md): Nx monorepo, Drizzle.
- Secrets include the Google client secret, the Discogs token and `LOOKUP_CONTACT_EMAIL` ([Lookup module and external API proxying](22-lookup-module.md)); local dev runs MinIO in `docker-compose`.
- [Sign-in for local development and e2e tests](23-dev-and-e2e-sign-in.md): e2e runs a self-contained stack per run (Postgres + MinIO containers, fake OIDC provider, e2e-only API entrypoint), Chromium only; workers and sharding decided here. Local dev needs a development Google OAuth client.

Decide:
- CI provider and what runs on a pull request (Nx affected lint/test/build, e2e),
- environments (production only, or staging / per-PR previews, incl. Neon branches) and how they get OAuth redirect URIs and cookies,
- when and how Drizzle migrations run, and rollback,
- where secrets live per environment,
- the DNS and domain setup steps.

## Answer

Resolved 2026-11-20 (grilling). No glossary terms, no ADR (CI and migration mechanics are cheap to change).

**Scope.** Production deployment is **out of scope for the MVP**: "MVP done" means it runs locally and CI is green on pull requests. The domain and DNS setup, the deploy job, Render Blueprint, database backups and rollback, and the Render plan are a separate, later effort. The hosting decisions ([Hosting and file storage](04-hosting-and-storage.md)) stay the target the code is written for: `__Host-` cookie, S3 adapter, Zod-validated config and `/health` are built now, so a later deploy is configuration, not rework.

**CI (GitHub Actions, modelled on Daylo's `ci.yml`).** On pull requests to `main` and pushes to `main`, with per-PR concurrency cancelling stale runs:
- conventions: commitlint on the PR title and the PR's commits (latest commit on `main`);
- quality: `nx affected -t lint test build` on PRs, `nx run-many -t lint test build` on `main`, plus a check that the Drizzle schema has no ungenerated migration;
- e2e: affected projects with the `e2e-fullstack` target ([Sign-in for local development and e2e tests](23-dev-and-e2e-sign-in.md)), Chromium installed in the job, one job with 2 Playwright workers, no sharding; add sharding once e2e takes more than ~10 minutes. Playwright reports uploaded on failure.

`main` is protected: changes land only through a PR with all checks green.

**Environments.** Local development (real Google with a development OAuth client, `docker-compose` with Postgres and MinIO) and the ephemeral per-run e2e stack in CI. No staging and no per-PR previews.

**Migrations.** Generated by `drizzle-kit generate` and committed. Applied by the programmatic Drizzle migrator when the API starts, before it listens, under a Postgres advisory lock. Rule **expand → contract**: every migration must work with the previous app version; destructive changes (dropping columns) go in a later release. No down migrations: fix forward.

**Periodic jobs** (image sweep from [Covers, photos and thumbnails](11-covers-photos-thumbnails.md), expired-session sweep from [Authentication and sessions](08-authentication.md)): run in-process at startup and every 24 h while the process lives, guarded by a "last run" row in the database so a job runs at most once a day; jobs are idempotent, so a missed day (e.g. a sleeping free instance) does no harm.

**Observability.** `GET /health` checks the database connection. Structured JSON logs. No Sentry or external uptime monitor in the MVP.

**Secrets and config.** Local: untracked `.env` copied from a committed `.env.example`, validated at startup by the same Zod config schema used everywhere. CI needs no application secrets (the e2e stack generates its own). For the later deploy effort, the agreed split: runtime secrets (Neon direct `DATABASE_URL`, Google client id/secret, Discogs token, `LOOKUP_CONTACT_EMAIL`, allowlist, R2 keys, `S3_ENDPOINT`, `IMAGE_BASE_URL`, `APP_ORIGIN`) in Render env vars; deploy credentials (Render, Cloudflare, Neon API) in GitHub Actions secrets; the frontend holds no secrets.

**Discussed, deferred with production deployment:** domain on Cloudflare DNS with `app.`/`api.` (DNS only)/`img.` and an apex redirect, production Google OAuth client; a deploy job deploying API (Render deploy hook for the SHA, wait for live) before the frontend (`wrangler pages deploy`); Neon pre-deploy snapshot branches; starting on Render Free and upgrading to Starter when cold starts hurt.
