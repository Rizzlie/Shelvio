# api-db

`@shelvio/api/db` (`scope:api`, `type:data-access`): every Drizzle table and the single migration stream. Each backend module's `domain` library touches only its own tables here, and reaches other modules' data through their operations.

- `src/lib/schema/`: one file per table or group of tables, all re-exported from `schema/index.ts` (the file `drizzle-kit` reads).
- `src/lib/columns.ts`: the column builders behind the conventions below.
- `migrations/`: generated SQL plus drizzle-kit's `meta/` snapshots. Commit all of it, and never edit a migration that has reached `main`.
- `@shelvio/api/db/testing`: Testcontainers helpers for spec files only.

## Table conventions

- **Ids**: `id: primaryId()`, a UUIDv7 generated by the API. The ids are time-ordered, so inserts append to the index. Postgres 17 has no `uuidv7()`, which is why there is no database default. Rows keyed by a natural name (such as `job_runs`) are the exception.
- **Timestamps**: main tables spread `...timestamps()`, which gives `created_at` and `updated_at` (`timestamptz`, from the database clock). `updated_at` moves forward on every Drizzle update.
- **Naming**: declare columns unnamed and in camelCase. The `snake_case` casing (`CASING`, shared by the runtime and `drizzle.config.ts`) names them in SQL.
- **Enums**: store an enum as text with a CHECK constraint, never as a Postgres enum. Its values come from the Zod const in `@shelvio/shared/contracts`, so the API contract and the database agree:

  ```ts
  import { OwnershipStatus } from '@shelvio/shared/contracts'; // z.enum([...])

  export const items = pgTable(
    'items',
    {
      id: primaryId(),
      ownershipStatus: textEnum(OwnershipStatus.options).notNull(),
      ...timestamps(),
    },
    (t) => [enumCheck('items_ownership_status_check', t.ownershipStatus, OwnershipStatus.options)],
  );
  ```

  Schema files may import from `@shelvio/shared/contracts`; drizzle-kit resolves the workspace path aliases. Adding a value to the const changes the constraint, so `generate-migration` emits a migration for it.

## Changing the schema

1. Edit the tables under `src/lib/schema/`.
2. Run `nx run api-db:generate-migration --name=<what_changed>` (for example `--name=add_items`).
3. Read the generated SQL, then commit it with the schema change.

The API applies pending migrations at startup, before it listens, under a Postgres advisory lock, so instances that start together apply each migration once. `DATABASE_URL` must therefore reach Postgres directly: a transaction-mode pooler (such as PgBouncer or Neon's `-pooler` host) doesn't keep session-level advisory locks.

CI runs `nx run api-db:check-migrations` and fails when the schema has changes that no committed migration covers, or when migrations conflict (for example, two branches that both added `0001`). If two branches conflict, delete the later branch's migration and regenerate it on top of the merged one. Don't just renumber it: the migrator only applies migrations newer than the latest one a database has, so a migration generated earlier but merged later would be skipped silently wherever the newer one already ran.

### Rules for every migration

- **Expand → contract.** Each migration must work with the _previous_ app version as well, because the old release keeps serving while the new one starts and migrates. Add first (a nullable column, a new table, a backfill), switch the code over in that release, and ship destructive steps (drop, rename, `NOT NULL` on existing data, a narrower CHECK) in a later release, once no running code depends on the old shape. A rename is therefore add + copy + later drop.
- **No down migrations; fix forward.** Nothing rolls a migration back. If one is wrong, write a new migration that corrects it.

## Testing with a real Postgres

Anything that persists is tested against a real Postgres in Docker (Testcontainers). Use `useTestDatabase()` in a spec file or `describe` block. It starts a container in `beforeAll`, applies the committed migrations and removes the container in `afterAll`:

```ts
import { useTestDatabase } from '@shelvio/api/db/testing';

describe('sweepExpiredSessions', () => {
  const database = useTestDatabase();

  it('removes expired sessions', async () => {
    // database.db: Drizzle handle; database.pool: raw pg Pool; database.url: for testConfig()
  });
});
```

Each file gets its own database, so tests in a file share state: create the rows each test needs instead of relying on an empty table. `startTestDatabase()` is the same fixture without the hooks. `useTestPostgres()` and `startPostgres()` give an empty, unmigrated container instead, for tests of the migrator or of generated SQL.

Docker must be running. Run `nx test api-db` for this library's tests.
